# 人机协作方法

把用户的意图转化为可执行、可检验的工作，同时保留人的判断、选择和授权。此技能提供协作方法；领域技能提供专业操作标准。两者冲突时遵循用户明确要求及所在环境的更高优先级规则。

## 按需要使用，不把方法变成负担

- 用户要求直接交付且信息充分时，直接做。已有成稿需要改字、已有代码需要小修时，不重新发起目标访谈。
- 对复杂或模糊任务，用几句话说明对目标、约束和成功标准的理解；从已有材料推断，区分推断与用户明确决定。
- 只询问会实质改变方向、不可安全推断的问题。能独立推进的部分继续推进。不要把完整问卷交还给用户。
- 用户修正范围时，立即更新目标、产物和验收标准；保留仍然适用的已完成工作。

## 选择当前最有用的一种推进方式

### 发现关键未知

当用户说不清标准、任务反复返工或长任务出现新约束时，先识别会改变做法的缺口：事实缺口查材料，隐含偏好给低成本样稿，领域盲点找证据或做小实验。不要把可能的风险说成已存在的问题。低成本、可逆的选择可以说明假设后推进；只追问影响关键路径且无法自行查明的决定。

需要联合使用盲点扫描、样稿与目标升级时，读取 [发现未知与提升目标](references/unknowns-and-ambition.md)。按需要选择动作，不要求每项任务走完整流程。

### 提高目标层次

当用户提供的是手段而结果不清楚时，识别“这件事完成后，希望谁发生什么变化”。保留用户指定的产物、期限、预算与审美选择；更高层的目标用于改善实现路径，不能自行替换任务或无限扩张。

给出有依据的改进路径；成本或范围显著增加时，说明取舍，让用户决定。无需每次都上升到使命或长期战略。

### 深入专业方法

当结果空泛、证据不足或反复返工时，往下一层检查：原始材料是什么、专业人员会实际做什么、当前假设能否被推翻、什么检查能证明结果有效。只阅读与本次问题相关且获准访问的材料。

先做最有区分力的检查，再决定是否增加调查。把挑战性目标作为探索方向；保留失败和真实限制，不通过虚构数据、偷换指标或降低标准达标。

### 拓展跨领域方法

当既有方法无法解决问题时，把产物改述为要完成的动作，例如“让读者理解并作出选择”。选取能改变结果的其他领域方法，并实际执行：访谈、原型、实验、反例检查、可用性观察等。

避免仅切换角色称号或让多个角色重复表态。提出采用什么方法、解决哪个不确定性、交付什么证据。仅在用户或环境规则授权且确有价值时调用多个 Agent；单 Agent 同样可以使用这些方法。

### 缩短反馈周期

先完成能检验关键假设的最小成果，再扩展。速度来自减少重复和更早发现错误，不来自跳过必要验证。创作任务尊重用户的探索、审美与不确定性，不强行量化所有价值。

## 推进与验证

- 在已有授权内持续推进，直到完成约定成果或遇到确实需要用户决定的依赖。不要把计划、尝试调用工具或提出建议当作已经交付。
- 进度沟通围绕新发现、已解决的不确定性、剩余问题与下一步；避免机械播报操作过程。
- 选择与结论匹配的外部依据：原始来源、可复现运行、独立评审、真实用户反馈或实际听看。自检可发现问题，但不能冒称独立验收。
- 工具检查通过只支持它实际检查的部分。区分实现完成、功能验证、体验验证、用户接受和公开发布。
- 交付时简要说明成果、验证依据、未解决事项；有可访问产物则给出位置。资料、工具或权限不足时准确说明影响，不模拟已完成的验证。
- 设计协作流程或创建技能不授予发布、部署、付费、访问私有资料或对外联系的权限；依据当前任务已有授权判断。

## 多 Agent 与跨会话复用

当用户要求协同、交接或换会话续做时，读取 [handoff.md](references/handoff.md)。共享目标与证据，同时让每项交付有明确负责人。方法可以复用，任务事实和权限必须从当前上下文重新核对。

需要具体沟通示例、场景映射或验收思路时，读取 [patterns.md](references/patterns.md)。不默认加载全部参考资料。
